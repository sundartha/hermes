### Phase P2 - withStoreLock-Reentrancy strukturell absichern (AsyncLocalStorage-Guard)

**Status: ERLEDIGT (2026-07-17)** - gemergt als `1d7992f` (Impl `94df97f`, Branch `phase/cc-p2-store-reentrancy`). Dualer Review: Opus-Safety-Review APPROVED, Clean-Code S1/S2 leer, 0 Fix-Runden. Suite 2318/0 (+4 Reentrancy-Tests). AsyncLocalStorage-Guard: verschachtelter withStoreLock wirft synchron, echte Nebenlaeufigkeit laeuft unveraendert (T3 gruen); chain-mutex.js + single-flight.js unangetastet. NICHT deployt.

**Ziel:** Die HARD-RULE "ein withStoreLock(fn)-Body darf NIE erneut withStoreLock aufrufen" (heute nur per Kommentar/Konvention durchgesetzt, src/store.js:193-195) strukturell erzwingen: ein verschachtelter Aufruf soll SOFORT und laut mit einem klaren Fehler abbrechen (Stack zeigt auf die schuldige Zeile), statt still einen prozessweiten Zirkel-Deadlock zu erzeugen, der alle folgenden Call-/Budget-/Transkript-Writes einfriert. Legitime nebenlaeufige (nicht verschachtelte) Aufrufe muessen unveraendert normal serialisiert durchlaufen.

**Abgedeckte Befund-IDs:** S1-11

**Betroffene Dateien:** src/store.js, test/store-lock-reentrancy.test.js

**Echte Wurzel:** runStoreExclusive = makeChainMutex() ist eine reine Promise-Kette (chain = chain.then(run, run)) OHNE jeden Zustand darueber, "wer den Lock gerade haelt". Ein withStoreLock-Aufruf, dessen fn() intern (direkt oder transitiv ueber await-Schichten) erneut withStoreLock aufruft, haengt eine neue .then() an dieselbe chain, die erst aufloest, wenn der AEUSSERE Aufruf fertig ist - der aber genau auf den inneren wartet: zirkulaerer Deadlock, prozessweit, ohne Fehlermeldung. Der Kern ist NICHT ein Bug im Code, sondern eine Invariante-per-Konvention (Audit-Muster G31/G27): die Nicht-Verschachtelung wird nur per Kommentar behauptet und musste in src/billing/webhook.js:254-259 real umschifft werden. Es gibt keine Laufzeit-Sicherung, die eine kuenftige verschachtelte Nutzung erkennt.

**Fix-Ansatz:** Reentrancy strukturell erkennbar machen - eng auf src/store.js/withStoreLock begrenzt, chain-mutex.js und single-flight.js bleiben UNANGETASTET. Werkzeug: node:async_hooks/AsyncLocalStorage (NICHT ein Modul-Level-Boolean-Flag, weil ein Flag legitime NEBENLAEUFIGE, nicht-verschachtelte Aufrufe faelschlich abweisen wuerde). Modul-lokale `const storeLockContext = new AsyncLocalStorage()`. withStoreLock(fn): (1) am Eintritt `if (storeLockContext.getStore()) throw new Error(...)` - synchron werfen, Stack zeigt auf den verschachtelten Aufrufer. (2) fn NICHT direkt an runStoreExclusive geben, sondern `runStoreExclusive(() => storeLockContext.run(REENTRANCY_MARKER, fn))` - Kontext wird pro Lauf frisch etabliert, wenn fn tatsaechlich startet. .then-Callbacks laufen im Kontext ihrer Registrierungsstelle, nicht dem des aufloesenden Promise -> ein nachrueckender legitimer Lauf B erbt NICHT A's Kontext. REENTRANCY_MARKER als benannte Modul-Konstante (Symbol). Keine Verhaltensaenderung fuer alle heutigen Aufrufer (alle Bodies sind synchron load->mutate->save, keiner verschachtelt).

**Tests:** Neue Datei test/store-lock-reentrancy.test.js. T1 (Kern): verschachtelter withStoreLock-Aufruf lehnt SCHNELL (Watchdog gegen kurzes setTimeout, nicht node:test-Timeout) mit reentrant-Fehler ab. T2 (kein prozessweites Einfrieren): NACH gescheitertem verschachteltem Aufruf laeuft ein folgender unabhaengiger withStoreLock normal durch. T3 (kein false-positive bei echter Nebenlaeufigkeit): zwei parallele, NICHT verschachtelte withStoreLock-Aufrufe laufen beide erfolgreich und serialisiert durch.
