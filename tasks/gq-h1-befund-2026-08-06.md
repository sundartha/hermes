# GQ-H1 — Das Haken (Kickoff 2026-08-07, P1)

## Ergebnis vorweg

**Die Praemisse von P1 traegt nicht.** Der Anrufer hat *nicht* drei Antworten gehoert. Telnyx
hat die zwei ueberzaehligen Turns verworfen, bevor sie gesprochen wurden. Was wirklich kaputt
ist, ist etwas anderes — und es steht in denselben Logs.

## Was gebaut wurde

`test/gq-h1-haken-repro.test.js` — Offline-Reproduktion, ~200 ms, kein Telefon, kein Netz.
Sie fuhr die Live-Zahlen exakt nach (3 Turns auf EINE wachsende Aeusserung, 2x
`no_inflight`). Sie bleibt gueltig, aber ihre Abnahme aendert sich (s. u.).

Live-Konfiguration gesichert: `data/evidence/telnyx-config/assistant-snapshot-2026-08-06-gq-h1.json`.

## Der Beleg

Telnyx' eigenes Gespraechsprotokoll (`GET /v2/ai/conversations/59553cc6-.../messages`,
Konversation zu `call_msgf3r21x0w0`) enthaelt **12 Nachrichten**. Gegen unsere `turn_probe`-
und `turn_ok`-Zeilen gestellt, ergibt sich eine luecklose 1:1-Zuordnung:

| system | :26:10,02 | turnSeq 1 | Anstoss |
| user / assistant | :26:12,6 / :26:14,4 | turnSeq 2 | |

| user / assistant | :26:29,9 / :26:31,3 | turnSeq **5** | turnSeq 4 fehlt |

**Genau die drei Turns, auf die eine `prevRelation:"extends"`-Fortsetzung folgte (4, 7, 8),
haben in Telnyx' Protokoll keine assistant-Nachricht.** Telnyx hat sie verworfen. Das deckt
sich mit der Anbieter-Doku zu Eager-EOT, woertlich: *"waiting for confirmed turn completion
before playback"* und *"Automatic fallback: Reverts to standard turn handling if the transcript
changes mid-turn"*.

Die Zahl "3 Antworten in 5 Sekunden" stammt aus **unserem** `transcript_segment` — wir
schreiben jeden Shim-Turn mit, auch die, die nie gesprochen wurden.

## Was daraus wirklich folgt (die echten Defekte)

1. **Verbrannte Modell-Turns.** In diesem einen Anruf liefen 8 substanzielle Turns, 3 davon
   umsonst (turnSeq 4, 7, 8): ~4,6 s Modellzeit und 3x ~4,3k Eingabe-Token, bezahlt und
   weggeworfen. Das sind **37 % der Turns dieses Anrufs**.
2. **Vergiftetes Gedaechtnis.** Unser Transkript und damit der Kontext des naechsten Turns,
   die Zusammenfassung und die Nachricht an den Owner enthalten Antworten, die der Anrufer
   **nie gehoert hat**. Ein Agent, dessen Kontext behauptet, er habe etwas bereits gesagt,
   verhaelt sich zwangslaeufig unsinnig. Das ist die bessere Erklaerung fuer das Owner-Urteil
   als Doppelsprechen — und sie erklaert auch, warum die Gegenstelle wirkte, als rede der
   Agent an ihr vorbei.
3. **Der Verdraengungs-Riegel (GQ-P1) ist wirkungslos und ueberfluessig.** `no_inflight` heisst
   hier nicht "zu spaet", sondern "Telnyx hat das Problem schon geloest". Er schuetzt vor
   einem Doppelsprechen, das es nicht gibt.

## Widerlegt

- **"Eager-EOT ist aus, weil `eot_threshold == eager_eot_threshold`."** Telnyx behauptet das
  (*"Set both thresholds to the same value to disable eager behavior"*), aber live stehen
  beide auf 0.9 **und Eager feuert trotzdem** — belegt durch die drei verworfenen Turns.
  Anbieter-Aussage und Anbieter-Verhalten widersprechen sich.
- **`eot_threshold` hat keinen Spielraum.** Deepgram-Wertebereich **0.5-0.9**, Default 0.7 —
  live steht das Maximum 0.9.
- **Eine Haltefrist im Code (P1b) waere der falsche Hebel.** Sie wuerde Latenz gegen ein
  Doppelsprechen tauschen, das nicht existiert.

## Offener Punkt

`eager_eot_threshold` laesst sich per API **nicht** loeschen: `PATCH` mit `null` liefert 200,
erzeugt eine neue Version (`20260806T074913520989`) und aendert den Wert nicht — Telnyx merged
tief, `null` heisst "nicht aendern". Gegengeprueft: die uebrige Assistant-Konfiguration ist
byte-identisch geblieben, nichts verloren. Weg bleibt das Mission-Control-Portal
(Voice -> Transcription) oder der Telnyx-Support.

## Naechste Schritte (Vorschlag, Owner entscheidet)

- **H1-a** Aufhoeren, verworfene Turns ins Transkript zu schreiben — bzw. sie als
  spekulativ markieren. Das ist der Defekt mit dem groessten Hebel und er liegt **in unserem
  Code**. Braucht kein Telefon zum Verifizieren.
- **H1-b** Eager-EOT im Portal abschalten und den Token-Verbrauch je Anruf messen (Erwartung:
  ~30 % weniger Modell-Turns, Gegenrechnung: Telnyx beziffert den Eager-Gewinn auf ~150 ms
  Median — bei 1,1-2,0 s Modell-Latenz ein schlechtes Geschaeft).
- **H1-c** Abnahme der Reproduktion umstellen: nicht "eine gesprochene Antwort", sondern
  **ein ausgefuehrter Modell-Turn je Aeusserung**.
