# Resources-Flaeche des MCP-Servers

## Kurzfassung

Der Server registriert genau 5 statische ui://-Resources (agent-status, my-number, calls,
calendar, call), EINE Registrierungsstelle (`src/ui/contract.js:60-77`), aufgerufen aus
`src/mcp-tools.js:620` fuer jedes UI-Tool. Gate ist der Master-Schalter `MCP_UI_ENABLED`
(Default `true`), Registrierung passiert pro Request neu (stateless), calendar zusaetzlich
gated durch das Tenant-Profil. `resources/list`/`resources/read` laufen ueber DIESELBE
`mcpAuth`-Middleware wie `tools/call` (ein Route-Handler, kein methodenspezifischer Gate).
Resource-INHALT ist tenant-frei (nur Sprache variiert) - Daten kommen ausschliesslich ueber
`structuredContent` je Tool-Aufruf, nie ueber die Resource selbst. Groessen-Falle bestaetigt
und live nachgemessen: bis zu ~247 KB pro `resources/read` (call-Widget), Ursache ein
~170-KB-PNG-Data-URI, im Code selbst als bekannt dokumentiert, bewusst nicht behoben.
OpenAI-Pflichtfelder fuer UI-Resources (`_meta.ui.csp`, `_meta.ui.domain`) fehlen vollstaendig.

## Pruefpunkte

### PP-D17-01 Welche Resources registriert der Server, mit welchem URI-Muster, Name, MIME-Typ und an welcher Stelle?
- Status: PASS
- Evidenz: Einzige Registrierungsstelle `server.registerResource(widgetId, uri, { title, mimeType }, readCallback)` in `src/ui/contract.js:70-75`, gebaut von der Fabrik `makeUiRenderer` (`src/ui/contract.js:60-77`). Aufgerufen aus `enableWidgetUi()` in `src/mcp-tools.js:606-620`, das wiederum an 5 Stellen in `src/mcp-tools.js` haengt: Zeile 822 (`place_call` -> `WIDGET_CALL`), 1074 (`get_my_number` -> `WIDGET_MY_NUMBER`), 1102 (`list_calls` -> `WIDGET_CALLS`), 1177 (`get_calendar` -> `WIDGET_CALENDAR`), 1216 (`get_agent_status` -> `WIDGET_AGENT_STATUS`). URI-Schema `ui://hermes/<widgetId>` (`UI_URI_PREFIX`, `uiResourceUri`, `src/ui/contract.js:19-20`). Name = der `widgetId`-String selbst (erstes Argument von `registerResource`); Title kommt aus `WIDGET_DEFS[widgetId].title` (`src/ui/widget-catalog.js:96-101`, z.B. "Hermes Agent Status", "Hermes Call"). MIME-Typ host-abhaengig: `text/html;profile=mcp-app` (`UI_MIME`, `src/ui/contract.js:10`, MCP-nativer Renderer, Default) oder `text/html+skybridge` (`CHATGPT_UI_MIME`, `src/ui/contract.js:47`, nur wenn der Client explizit die Skybridge-Capability meldet, `src/ui/registry.js:43-49`). Grep ueber `src/` nach `ResourceTemplate`/`registerResourceTemplate` = 0 Treffer - keine dynamischen Resource-Templates, nur 5 statische Resources je Request.
- Risiko: keines - Inventar ist die Basis fuer PP-D17-02 bis -06.
- Empfehlung: Zustand halten; neue Widgets folgen demselben `WIDGET_DEFS`-Eintrag statt einer zweiten Registrierungsstelle.
- Prioritaet/Kategorie: - / B

### PP-D17-02 Haengt die Registrierung an einem Flag, was ist der Default, ist die Liste client- oder zustandsabhaengig?
- Status: PARTIAL
- Evidenz: Master-Schalter `config.tenancy.mcpUiEnabled` = `boolEnv("MCP_UI_ENABLED", ..., { fallback: true })` (`src/config.js:1574-1575`), `.env.example:326` dokumentiert `MCP_UI_ENABLED=true`. Aus -> `uiRendererFor()` liefert `null` (`src/ui/registry.js:43-45`), `enableWidgetUi()` liefert `{}` ohne Resource-Registrierung (`src/mcp-tools.js:611-620`) - 0 Resources, byte-identisch zum Vor-UI-Zustand. An -> die Resource-Registrierung passiert NEU BEI JEDEM `/mcp`-POST (`server.connect`/`registerTools` pro Request, `src/routes/mcp.js:96-118`, Kommentarblock Zeile 7-11 "STATELESS ... KEIN Hoisting/Caching ueber Requests"), nicht einmalig beim Boot. Damit ist die Liste **zustandsabhaengig** in genau einer Dimension: `get_calendar`/`WIDGET_CALENDAR` wird nur registriert, wenn `allowCalendar` (aus `store.resolveProfile(scopedTenant)`, `src/routes/mcp.js:76,108`) true ist (`if (allowCalendar) uiTool("get_calendar", ...)`, `src/mcp-tools.js:1170-1177`); die anderen 4 Widgets sind unbedingt. Client-Capabilities (`req.body?.params?.capabilities`, `src/routes/mcp.js:104`) veraendern NICHT die Menge der Resources, nur den Adapter (mimeType/`_meta`-Form) fuer alle 5 gleich (`src/ui/registry.js:47-49`). PARTIAL statt PASS, weil `allowCalendar` seinerseits vom Tenant-Profil-Resolving haengt, das laut `tasks/openai-audit/07-autorisierung-isolation.md` PP-D7-02 bei `MULTI_TENANT=false` (Default, `src/config.js:1570`) IMMER auf den Bootstrap-/Owner-Tenant kollabiert - in der Default-Konfiguration ist `allowCalendar` damit faktisch konstant `true` und die Resource-Liste wieder statisch. Nicht separat neu geprueft, siehe Verweis.
- Risiko: gering fuer die Resource-Flaeche isoliert; das Risiko liegt in der geerbten Tenant-Kollaps-Frage (bereits in D7 P0 gefuehrt), nicht in einer neuen Luecke hier.
- Empfehlung: bei einer Behebung von D7-PP-02 (MULTI_TENANT-Default) mitpruefen, ob `allowCalendar` dann tatsaechlich pro Tenant variiert und ob ein Client daraus auf Tenant-Merkmale schliessen kann (Resource-Praesenz als Seitenkanal) - reine Empfehlung, keine belegte OpenAI-Pflicht.
- Prioritaet/Kategorie: P2 / C

### PP-D17-03 Welche Auth gilt fuer resources/list und resources/read - dieselbe wie fuer Tools oder eine andere Stelle?
- Status: PASS
- Evidenz: Es gibt nur EINE Route, `router.post("/mcp", mcpAuth, async (req, res) => {...})` (`src/routes/mcp.js:51`). `mcpAuth` (`src/auth.js:95-114`) prueft den gesamten Request BEVOR der Body ueberhaupt als JSON-RPC interpretiert wird (oauth/token/legacy-Zweige, `safeEqual`-Vergleich Zeile 101). Danach wird EIN `McpServer` gebaut und `transport.handleRequest(req, res, req.body)` aufgerufen (`src/routes/mcp.js:118-119`) - das SDK dispatcht `resources/list` und `resources/read` intern ueber denselben, bereits authentifizierten Request (`node_modules/@modelcontextprotocol/sdk/dist/esm/server/mcp.js:339-380`: `registerCapabilities({ resources: { listChanged: true } })` plus die `ListResources`/`ReadResource`-Handler, beide lesen aus derselben `_registeredResources`-Map, die `contract.js:70` befuellt). Es existiert in `src/` **keine** zweite, methodenspezifische Pruefung fuer `resources/*` (Grep nach `"resources/list"`, `"resources/read"`, `ListResourcesRequestSchema`, `ReadResourceRequestSchema` in `src/` = 0 Treffer - das SDK, nicht Hermes-Code, bedient diese Methoden). `GET`/`DELETE /mcp` tragen bewusst keine Auth (nur 405, `src/routes/mcp.js:128-131`, in `src/route-policy.js:237-245` als `MCP_METHOD_NOT_ALLOWED_REASON` eingetragen) - das betrifft aber nicht `resources/read`, das ausschliesslich per POST laeuft.
- Risiko: keines eigenstaendiges; die Auth-Staerke fuer resources ist identisch zur Auth-Staerke fuer tools (bereits in `06-authentifizierung.md`/`07-autorisierung-isolation.md` bewertet, dort inkl. der `MULTI_TENANT=false`-Kollaps-Warnung, die genauso fuer resources gilt, weil derselbe `scopedTenant` in `registerTools()` einfliesst, s. PP-D17-02).
- Empfehlung: keine zusaetzliche - Zustand halten, kein separates Resource-Gate einfuehren (waere zusaetzliche Flaeche ohne Mehrwert, da SDK-intern ohnehin an dieselbe Session gebunden).
- Prioritaet/Kategorie: - / B

### PP-D17-04 Sind Ressourcen mandantengebunden? Kann ein Tenant eine Ressource eines anderen lesen? Enthalten Inhalte Tenant-Daten?
- Status: PASS
- Evidenz: Der URI ist laut Kommentar bewusst "EIN Tenant-freier, statischer URI je Widget" (`src/ui/contract.js:18`). `widgetHtml(widgetId, language)` ist NUR ueber `widgetId` + `language` indiziert (`src/ui/widget-catalog.js:170-177`, `WIDGET_HTML_BY_LOCALE`), kein Tenant-Schluessel existiert in dieser Struktur. Der Read-Callback liefert exakt dieses vorab (beim Modul-Load bzw. am `enableWidgetUi`-Aufruf) berechnete HTML zurueck, ohne je auf `scopedTenant`/`identity` zuzugreifen (`src/ui/contract.js:68-75`: Closure faengt nur `widgetId`+`language`, kein `identity`/`scopedTenant`-Parameter vorhanden). Tenant-/Anruf-Daten fliessen nachweislich NICHT durch die Resource, sondern ausschliesslich durch `structuredContent` je Tool-Antwort (`_meta`-Kommentar `src/ui/contract.js:20`: "Daten fliessen ueber structuredContent"), client-seitig gebunden per `postMessage` (`src/ui/widget-bind.js:1-16`: Host pusht `ui/notifications/tool-result`, Bindung ausschliesslich ueber `textContent`, nie `innerHTML`, kein serverseitiges Templating mit Tenant-Werten). Damit: JA, zwei Tenants (bzw. ein Tenant und ein Fremder mit gueltigem Token) erhalten beim Lesen derselben URI (z.B. `ui://hermes/call`) byte-identisches HTML fuer dieselbe Sprache - das ist kein IDOR, weil kein tenant-spezifischer Inhalt existiert, der lesbar waere.
- Risiko: keines in der Resource selbst. Das eigentliche Datenrisiko (Zugriff auf fremde `structuredContent`/Tool-Ergebnisse) ist ein Tool-, kein Resource-Befund und liegt bereits in `07-autorisierung-isolation.md` PP-D7-02 (P0) dokumentiert - dort gilt es unveraendert weiter, weil derselbe `scopedTenant`/`allowCalendar`-Pfad auch die Tool-Handler speist, die die eigentlichen Daten ausliefern.
- Empfehlung: Zustand halten; bei einem kuenftigen personalisierten Widget (falls je gebaut) muesste die Resource-URI selbst tenant-scoped werden (heute nicht der Fall, aktuell auch nicht noetig).
- Prioritaet/Kategorie: - / B

### PP-D17-05 Wie gross sind die ausgelieferten Inhalte? Gibt es die dokumentierte Groessen-Falle?
- Status: PARTIAL
- Evidenz: Live gemessen (`node --eval`, `widgetHtml(id, lang)` fuer alle 5 Widgets x 3 Sprachen, gegen den aktuellen Code-Stand): agent-status 214.100-215.265 Bytes, my-number 212.177-213.342 Bytes, calls 213.333-214.498 Bytes, calendar 212.650-213.815 Bytes, **call 246.398-247.563 Bytes** (UTF-8, alle Sprachen de-DE/en/fr). Root Cause im Code selbst benannt: `src/ui/widget-catalog.js:134` - Kommentar "inkl. des ca. 170 KB WING_PNG-Data-URI"; die Konstante liegt in `src/ui/wing-image-data.js:8` (`export const WING_PNG = "data:image/png;base64,..."`, Datei 171.712 Bytes gesamt) und wird ueber `withWingAssets()`/`WING_ASSETS_BY_VARIANT` in JEDES der 5 Widget-HTMLs einkopiert (`src/ui/widget-catalog.js:126-136`). Jeder `resources/read`-Call liefert also das komplette Base64-PNG als Teil des JSON-RPC-Response-Textkoerpers, nicht als separate/gecachte Binaerressource. Der Befund selbst ist NUR als Code-Kommentar im Repo dokumentiert (`widget-catalog.js:134`) - eine `tasks/`/`docs/`-Doku dazu wurde beim Repo-Aufraeumen 2026-09-12 bereits entfernt (nur noch in Session-Memory ausserhalb des Repos referenzierbar, dort nicht als Code-Evidenz zaehlbar). Status PARTIAL statt FAIL: die Groesse liegt weit unter jedem MCP/JSON-Limit (keine belegte harte Grenze verletzt) und ist bewusst nicht als P0 eingestuft (Owner-Entscheidung laut Commit-Historie, s. `widget-wire`-Kette) - aber es ist unveraendert eine unnoetig grosse, wiederholt inline ausgelieferte Payload ohne Caching.
- Risiko: Bandbreite/Latenz pro Widget-Resource-Read (~215-248 KB je Aufruf, 5x taeglich denkbar bei Millionen-Skala relevant), kein Sicherheits- oder Daten-Risiko.
- Empfehlung: Das PNG als separate, cachebare Binaerressource (eigene `image/png`-Resource statt inline Data-URI) ausliefern oder komprimieren/verkleinern - Empfehlung (Kategorie C), keine belegte OpenAI-Pflicht.
- Prioritaet/Kategorie: P2 / C

### PP-D17-06 Was versteht ein fremder Client (ChatGPT), was ist Claude-spezifisch?
- Status: PARTIAL
- Evidenz: `tasks/openai-audit/00-openai-anforderungen.md` Zeile 181-182 (Abschnitt "nicht auffindbar"): der Unterstuetzungsstatus von `resources` in ChatGPT ist laut dortiger Recherche generell unklar, "nur `tools`, `resources` fuer UI-Templates ... sind belegt" - Hermes' Nutzung (Widget-HTML als `text/html+skybridge`-Resource) entspricht genau diesem belegten Fall. Format-seitig unterscheidet Hermes bereits explizit zwischen den Konventionen: MCP-nativ traegt `_meta.ui.resourceUri` (verschachtelt, `UI_META_KEY = "ui"`, `src/ui/contract.js:15`), ChatGPT traegt denselben URI flach unter `_meta["openai/outputTemplate"]` (`CHATGPT_META_KEY`, `src/ui/contract.js:50`) - deckt sich mit der dokumentierten OpenAI-Anforderung T-23 (`00-openai-anforderungen.md` Zeile: "Prefer `_meta.ui.resourceUri` ... `openai/outputTemplate` nur als Kompatibilitaets-Alias"). ABER: zwei von OpenAI als Kategorie-A ("belegte Pflicht") gefuehrte UI-Resource-Anforderungen fehlen vollstaendig im Code - T-30 (`_meta.ui.csp` mit `connectDomains`/`resourceDomains`) und T-31 (`_meta.ui.domain`, pro Plugin eindeutiger Origin), beide `00-openai-anforderungen.md` Zeilen mit Quelle `plugins/deploy/app-review` bzw. `plugins/reference`. Grep ueber `src/` nach `ui.csp`, `ui.domain`, `connectDomains`, `resourceDomains` = 0 Treffer (nur `outputTemplate`/`resourceUri` existieren, `src/ui/adapters/mcp-native.js:9-13`, `src/ui/adapters/chatgpt.js:6-10`). Claude-spezifisch UND ungenutzt bei ChatGPT: das Self-Polling/Live-Update-Muster des Call-Widgets ist laut `src/ui/registry.js:14-33` (Kommentarblock) fuer den ChatGPT-Host bewusst STUMM belassen ("bleibt dort STUMM, weil kein Host-seitiger Bridge-Code dieses Wire-Format entgegennimmt") - ein echter ChatGPT-Client bekaeme nur den initialen Tool-Text/`structuredContent`, keine sich aktualisierende Karte.
- Risiko: fuer eine tatsaechliche OpenAI-Plugin-Einreichung waere das Fehlen von `ui.csp`/`ui.domain` ein Einreichungs-Blocker (laut den dortigen Kategorie-A-Eintraegen); fuer den heutigen Claude-only-Betrieb kein Laufzeitrisiko.
- Empfehlung: NUR falls ein ChatGPT-Rollout ansteht: `_meta.ui.csp` und `_meta.ui.domain` im `chatgptRenderer` ergaenzen (`src/ui/adapters/chatgpt.js`), vorher pruefen, ob T-30/T-31 fuer Developer-Mode-Connectors (statt Public-Plugin-Submission) ueberhaupt gelten - das ist in `00-openai-anforderungen.md` selbst nicht klar getrennt. Empfehlung, keine akute Pflicht fuer den aktuellen Claude-Betrieb.
- Prioritaet/Kategorie: P1 / A (fuer den Fall einer OpenAI-Einreichung; A, weil T-30/T-31 dort selbst als "A" gefuehrt werden - nicht neu bewertet)
