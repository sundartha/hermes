## Wurzel, am Code belegt

`src/telnyx-inbound.js:13`:


Der Kommentar direkt darueber (Zeile 9-12) sagt es selbst: "Telnyx-TeXML-Inbound-Body-Feld
mit der call_control_id des Inbound-Legs. Doku-Stand, live unbestaetigt (wie der ganze

fail-safe auf den bestehenden TeXML-Greeting-Pfad zurueck (byte-identisch), kein kaputter
Assistant-Pfad."

Der Aufrufer ist `inboundAssistantHandoffXml` in `src/routes/voice.js:167-173`:

```js
async function inboundAssistantHandoffXml({ call, provider, body, greeting, voiceProfile }) {
  if (!(config.telnyx.telnyxAssistant.enabled && providerSupports(provider, CAPABILITY.AI_ASSISTANT))) return null;
  const callControlId = inboundCallControlId(body);
  if (!callControlId) return null;
  await startInboundAiAssistant({ store, voiceControl, config, call, callControlId, greeting, voiceProfile });
  return render(INBOUND_ASSISTANT_HANDOFF, provider);
}
```

`inboundCallControlId` (telnyx-inbound.js:15-18) liest `body["CallControlId"]`. Ist das
Feld im echten Telnyx-TeXML-Webhook anders benannt (z.B. `call_control_id`, klein, oder
gar nicht im ersten `/voice/incoming`-POST enthalten, sondern erst in einem spaeteren
Call-Control-Event), liefert der Lookup `undefined` -> `inboundCallControlId` gibt `null`
zurueck -> `inboundAssistantHandoffXml` gibt `null` zurueck (Zeile 170) -> der Aufrufer in
`voice.js:328` faellt auf `turnDirectives`/Budget-Engine zurueck (Zeile 330-331). Dieser
Rueckfall ist **komplett still**: kein Log, keine Metrik, kein Unterschied im
HTTP-Response-Code. Der Betreiber sieht "Flag AKTIV" in der Config und bekommt trotzdem
seit Wochen jeden Inbound-Call ueber die Budget-Engine (TeXML-Gather+STT) bedient - exakt
das im Log beobachtete Bild (assistant_id/telnyx_conversation_id NULL, keine
`turn_ok`-Zeile, Pausen 10827/17839/12671 ms statt der 1036-2846 ms Modell-Latenz).

## Antworten auf die drei Fragen

### 1. Wie misst man den echten Feldnamen, ohne zu raten?

Es gibt AKTUELL KEINE Stelle, an der der rohe Inbound-Body schon geloggt wird (bestaetigt
per grep). Der Handgriff muss also eine TEMPORAERE Sonde sein, keine Wiederverwendung von
Bestehendem:

- In `src/routes/voice.js`, im `/voice/incoming`-Handler (nach `numberRecordByE164`, wo
  `provider` und der Telnyx-Zweig schon feststehen, z.B. direkt vor der bestehenden
  `inboundAssistantHandoffXml`-Aufrufstelle Zeile 321), EINE Zeile:
  `console.log("[b9-probe] inbound body keys", Object.keys(req.body || {}))` -
  ausschliesslich unter `if (provider === PROVIDER.TELNYX)`, damit kein Twilio-Traffic
  mitgeloggt wird.
- KEINE Werte loggen, nur `Object.keys(...)` - der Body kann PII (Anrufer-Nummer,
  Metadaten) enthalten, Regel 4 verbietet das Leaken von potenziell sensiblen Rohdaten;
  Feldnamen sind unkritisch.
- Einen einzigen echten Testanruf auf eine Telnyx-Inbound-Nummer ausloesen (der Owner
  muss das tun, nicht ich - ich fasse keinen Code/Server an), Render-Log lesen, den
  wirklichen Schluessel ablesen, DANN die Sonde wieder entfernen (Wegwerf-Code hat in
  diesem Repo nichts verloren, s. CLAUDE.md "kein Wegwerf-Code" bzw. hier: kein
  dauerhafter Debug-Log).
- Alternative ohne Produktions-Traffic: Telnyx' TeXML-Webhook-Simulator/Sandbox (falls im
  Telnyx-Portal vorhanden) gegen eine `SKIP_TWILIO_SIGNATURE_CHECK=true`-lokale Instanz -
  aber das ist ausserhalb meiner Pruefbarkeit in dieser reinen Lese-Session, nur als
  Hinweis fuer die Umsetzungsphase.
- Falls der Name tatsaechlich `call_control_id` (Snake Case, wie der Rest der
  Telnyx-Call-Control-API es sonst durchgaengig nutzt, siehe `bindAssistantToCall`,
  `hangUpAction(callControlId)` etc.) ist statt `CallControlId` (Pascal, TeXML-Twilio-Stil)
  - das waere plausibel, ist aber eine HYPOTHESE, keine Messung. Nicht als Fix einsetzen
  ohne den Sondentreffer.

### 2. Was muss sichtbar werden, damit ein ausbleibender Handoff nicht mehr still ist?

Zwei Stellen in `inboundAssistantHandoffXml` (voice.js:167-173) fallen heute wortlos
durch:
- Flag/Capability aus (Zeile 168) - das ist GEWOLLTES Verhalten (Flag aus = alte Engine),
  braucht kein Log.
- `callControlId` fehlt trotz aktivem Flag+Capability (Zeile 169-170) - das ist der
  Defekt-Fall aus B-9. Hier fehlt eine sichtbare Zeile nach dem Muster der bestehenden
  OBS-3-Zeile (voice.js:219-221): eine PII-freie `console.warn` ODER `audit(...)` mit
  festem Ereignis-Namen (z.B. `inbound_assistant_handoff_skipped`), OHNE Body-Inhalt,
  NUR `call.id`/Provider/Tenant-frei oder mit gehashter Kennung falls noetig.
- Zusaetzlich: eine Zaehler-/Metrik-Sonde (falls das Repo schon Metriken fuehrt - `metrics`
  wird in voice.js bereits importiert/genutzt, Zeile 149 `metrics.recordTurnRendered`),
  damit ein Dashboard/Alert den Fall SEHEN kann, statt dass jemand Logs gruppen muesste.
  Ob ein solcher Metrik-Zaehler schon existiert oder neu angelegt werden muss, habe ich
  NICHT geprueft (ausserhalb meines Befund-Scopes, gehoert in die Umsetzungsphase).

### 3. Welche Dateien beruehrt das Scharfschalten?

- `src/telnyx-inbound.js` - den Feldnamen `INBOUND_CALL_CONTROL_ID_FIELD` auf den

- `src/routes/voice.js` - die sichtbare Log-/Audit-Zeile im Fehlschlagfall von

**Capability-Waechter im Weg (Merkposten fuer O-2, NICHT hier loesen):**

unangetastet vom B-9-Fix - das Scharfschalten des Feldnamens wirkt ausschliesslich auf
den Telnyx-Zweig. Kein Aenderungsbedarf am Waechter selbst fuer B-9.

## Loesungsskizze (fuer die Umsetzungsphase, nicht hier umgesetzt)

1. Sonde einbauen (temporaer), einen echten Testanruf ausloesen, Feldnamen ablesen,
   Sonde wieder entfernen.
2. `INBOUND_CALL_CONTROL_ID_FIELD` auf den gemessenen Wert setzen, Kommentar aktualisieren.
3. Sichtbare Log-/Audit-Zeile fuer den Skip-Fall (`callControlId` fehlt trotz aktivem
   Flag+Capability) ergaenzen.
4. Test: ein Fixture mit dem korrekten Feldnamen bestaetigt den Handoff-Pfad; ein Fixture
   ohne das Feld bestaetigt den NEUEN sichtbaren Log-Eintrag (statt nur stillem `null`).
5. Deploy, echten Anruf gegenpruefen: assistant_id/telnyx_conversation_id gesetzt,
   `turn_ok`-Zeilen im Log.

## Rueckweg

Der bestehende Fail-safe bleibt unveraendert: fehlt `callControlId` (auch nach der
Korrektur, z.B. bei einem kuenftigen Telnyx-API-Wechsel), faellt der Call weiterhin auf
die Budget-Engine zurueck (`voice.js:328`, `null` -> `turnDirectives`). Der einzige
Unterschied nach dem Fix: dieser Rueckfall ist dann LOGGED statt still. Ein Revert ist ein
reiner String-Rueckbau in `telnyx-inbound.js:13` plus Entfernen der neuen Log-Zeile -
keine strukturelle Aenderung, kein Safety-Gate beruehrt.

## Risiko / Safety-Gates

Beruehrt KEINE Safety-Gates direkt (Kostendecke, OUTBOUND_FROZEN, Signaturpruefung,
Offenlegungssatz, Auth bleiben unveraendert). Der Inbound-Assistant-Pfad ERBT laut
Kommentar (voice.js:158-160) Signatur- und Budget-Gate vom Aufrufer, fuegt keine neuen
hinzu - das gilt vor UND nach dem Fix gleichermassen. Indirektes Kostenrisiko: schaltet
der Fix den Assistant-Pfad live scharf, aendert sich die Kostenstruktur pro Inbound-Call
(Telnyx-Assistant/LLM-Shim statt Budget-Engine/Gather+STT) - das ist gewollter Zweck von
O-1, aber die pro-Tenant-Kostendecke (Regel 1, Absatz 2) bleibt die einzige Bremse dagegen
und ist bereits vor dem Handoff durchlaufen (voice.js:274-278, `store.budgetExceeded`),
unveraendert von diesem Befund.
