# B-2: get_consult erkennt seinen Anlass nicht

## Wurzel (Datei:Zeile)

Der Entscheidungspunkt ist NICHT im Prompt oder im Tool-Loop, sondern im
Registrierungs-Gate `consultAvailableFor` in `src/consult/in-call.js:65-75`:

```
export function consultAvailableFor(call, nowMs = Date.now()) {
  return (
    config.tenancy.inCallConsultEnabled === true &&
    consultAllowedFor(store.resolveProfile(call.tenantId)) &&
    call.direction === "outbound" &&
    call.status === "active" &&
    callAnswered(call) &&
    consultClientIsPolling(call, nowMs) &&
    inCallConsults(call).length < MAX_IN_CALL_CONSULTS_PER_CALL
  );
}
```

Aufgerufen in `src/claude.js:465`:
```
if (consultAvailableFor(call)) tools.push(getConsultToolDef(call.language));
```

D.h. `get_consult` wird dem Modell in einem Turn nur dann UEBERHAUPT im
Werkzeugsatz angeboten, wenn ALLE sechs Bedingungen zutreffen - insbesondere
`consultClientIsPolling(call, nowMs)` (`src/consult/in-call.js:56-58`):

```
export function consultClientIsPolling(call, nowMs = Date.now()) {
  return nowMs - (call.consultPolledAtMs || 0) <= CONSULT_POLL_FRESH_MS;
}
```

`consultPolledAtMs` wird ausschliesslich in `src/store/state-ops.js:817` per
`noteConsultPoll()` gesetzt - und zwar nur dann, wenn der MCP-Client des
Owners in genau diesem Moment aktiv `await_call_event` fuer den laufenden
Call abfragt (vgl. MCP-Serverinstruktion: "keep calling await_call_event ...
again and again"). `CONSULT_POLL_FRESH_MS = CONSULT_POLL_ABORT_MS`
(`src/consult/in-call.js:37`, Wert kommt aus `src/consult/delivery.js:20`,
zusammengesetzt aus `CONSULT_POLL_HOLD_MS + CONSULT_POLL_ABORT_MARGIN_MS` -
Werte selbst NICHT nachgelesen, s.u.).

**Strukturelle Folge:** Wenn der Owner den Anruf nicht gerade in diesem
Moment per eigener Claude-Session aktiv im await_call_event-Loop haelt
(z.B. weil er per normalem Telefon zuhoert, weil sein MCP-Client zwischen
zwei Polls kurz pausiert, oder weil der Testanruf ueberhaupt nicht ueber
`place_call`+Polling-Loop lief), ist `consultAvailableFor` false und
`get_consult` erscheint in `tools` fuer diesen Turn GAR NICHT. Haiku
"entscheidet" sich dann nicht gegen get_consult zugunsten von take_message
- es hat die Option nie gesehen. Das erklaert zwanglos, warum es im
19-Turn-Anruf genau einmal feuerte: vermutlich der einzige Moment, in dem
zufaellig ein frischer Poll vorlag - und warum es erst feuerte, nachdem die
Gegenstelle den Werkzeugnamen woertlich nannte (Zufallstreffer auf ein
Zeitfenster, kein Kausalzusammenhang mit der Nennung selbst, aber nicht
auszuschliessen dass die Verzoegerung durch das Aussprechen den Poll-Rhythmus
zufaellig traf).

Diese Analyse deckt sich mit `tasks/al-chain-state.md` (AL-D3): "Systemprompt
als Ursache widerlegt, Prompt-Hebel ausgereizt -> Diagnose statt
Formulierung" - das Poll-Freshness-Gate ist genau die strukturelle Ursache,
die dort gesucht, aber (soweit hier einsehbar) nicht bis zu dieser Zeile
verfolgt wurde.

## Was geprueft wurde

- `src/claude.js`: Tool-Registrierung (Zeile 388, 446-466), ALLOWLIST-Kommentar
  (338-388), Konkurrenz mit take_message (kein direkter Konflikt im Code -
  beide stehen gleichzeitig im Tool-Array, wenn get_consult verfuegbar ist;
  die "Konkurrenz" ist also eine Modell-Entscheidung NUR in den seltenen
  Turns, wo get_consult ueberhaupt sichtbar ist)
- `src/consult/in-call.js`: komplettes Gate `consultAvailableFor` (65-75),
  `consultClientIsPolling` (56-58), `requestConsult`-Ablauf (113-120,
  ueberflogen)
- `src/store/state-ops.js`: `noteConsultPoll` (813-816), Default-Init
  `consultPolledAtMs: 0` (305)
- MCP-Serverinstruktion (system-reminder dieser Session): bestaetigt, dass
  das Polling-Muster ("keep calling await_call_event, again and again")
  vom Client-Verhalten des Owners abhaengt, nicht vom Agenten im Call

## Was NICHT geprueft wurde

- Der konkrete Zahlenwert von `CONSULT_POLL_HOLD_MS` und
  `CONSULT_POLL_ABORT_MARGIN_MS` (`src/consult/delivery.js`) - also die
  tatsaechliche Frischefenster-Breite in ms. Ohne diese Zahl laesst sich
  nicht sagen, ob das Fenster z.B. so eng ist, dass es bei normalem
  MCP-Poll-Intervall systematisch verfehlt wird, oder ob es in der Praxis
  fast immer offen ist und nur bei diesem einen Testanruf zufaellig zu war.
- Wie/ob der 19-Turn-Testanruf tatsaechlich ueber `place_call` +
  `await_call_event`-Loop lief, oder ob der Owner reingehoert hat ohne
  aktiv MCP zu pollen (Anrufrichtung: das Praedikat verlangt zusaetzlich
  `call.direction === "outbound"` - bei einem Inbound-Testanruf waere
  get_consult UNABHAENGIG vom Polling nie verfuegbar; ob der Testanruf
  outbound war, ist aus dem Auftrag nicht ersichtlich und nicht geprueft)
- `inCallConsults(call).length < MAX_IN_CALL_CONSULTS_PER_CALL` (Kontingent
  = 1 pro Call, `src/consult/in-call.js:41`) - nicht geprueft, ob dieses
  Kontingent im 19-Turn-Anruf schon vor dem einen Treffer verbraucht war
  (waere ein weiterer, unabhaengiger Grund fuer "nur einmal")
- `consultAllowedFor(store.resolveProfile(...))` und
  `config.tenancy.inCallConsultEnabled` - Feature-Flag- und Profil-Gate,
  nicht inhaltlich verifiziert, nur als vorhanden zur Kenntnis genommen

## Loesungsskizze (keine Umsetzung, nur Skizze)

Die Wurzel ist eine PRODUKT-/PROTOKOLL-Frage, keine Prompt-Frage: get_consult
ist so gebaut, dass es strukturell voraussetzt, dass ein Mensch (der Owner)
in Echtzeit per MCP-Client zuhoert und pollt. Ein "autonomer" Agent im Sinne
des Owners ("er soll selbststaendig merken, wenn er eine Information nicht
weiss") braucht entweder:
(a) einen asynchronen Consult-Mechanismus, der NICHT an Live-Polling-
    Frische gebunden ist (z.B. Frage in Warteschlange legen, Anruf wartet
    ohne Timeout-Kopplung an Polling-Frische), oder
(b) eine bewusste Produktentscheidung, dass get_consult nur in einem
    begleiteten Testmodus sinnvoll ist und im echten Autonomiebetrieb
    strukturell WEGFAELLT (dann ist "es feuert kaum" kein Bug, sondern
    erwartetes Verhalten einer Funktion fuer einen anderen Use-Case) -
    diese Entscheidung ist Owner-Sache, nicht Code-Sache.
Vor jedem Fix: Owner fragen, welcher Use-Case gemeint ist - "live
begleiteter Anruf" oder "voll autonomer Anruf ohne Zuhoerer".
