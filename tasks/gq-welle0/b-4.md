# B-4: look_up feuert nie

## Wurzel (am Code belegt)

`src/research/in-call.js:60-70`, Funktion `lookupProviderFor(call)`:

```
export function lookupProviderFor(call) {
  if (config.research.lookupEnabled !== true) return null;
  if (config.tenancy.assistantContextEnabled !== true) return null;
  if (config.voice.voiceEngine === VOICE_ENGINE.REALTIME) return null;
  if (call.direction !== "outbound") return null;   // <-- Zeile 64
  if (call.status !== "active") return null;
  if (callLookups(call) >= LOOKUP_MAX_PER_CALL) return null;
  return inCallSearchProvider({...});
}
export const lookupAvailableFor = (call) => lookupProviderFor(call) !== null;
```

`call.direction !== "outbound"` schliesst JEDEN Inbound-Anruf aus, ausnahmslos. Das ist
kein Nebeneffekt, sondern ein bewusst gesetztes Gate mit Begruendung im Kopfkommentar
(Zeile ~40-45): "Das Richtungs-Gate ist der Sicherheitskern: eine im Gespraech mit einem
FREMDEN Inbound-Anrufer entstandene Frage darf nie an einen Suchindex gehen."

`lookupAvailableFor(call)` speist sowohl den Werkzeugsatz (`src/claude.js:79`, `agentTools`
via `lookupAvailable`) als auch die GRENZEN-Prompt-Zeile (dieselbe Quelle, G5-Prinzip laut
Kommentar `src/claude.js:73-83`) — bei Inbound wird look_up also weder angeboten noch im
Prompt erwaehnt, konsistent.

Der Owner-Testanruf war laut Kontextbeschreibung ein Anruf, bei dem der Owner selbst
angerufen hat/angerufen wurde und Fragen wie "Wann wurde Fiat gegruendet?" gestellt hat.
Wenn dieser Testanruf ein INBOUND-Call war (Owner ruft seine eigene Hermes-Nummer an, um
zu testen — das ist der uebliche manuelle Testablauf in diesem Repo, s.
`SKIP_TWILIO_SIGNATURE_CHECK` + curl-Hinweis in CLAUDE.md, oder ein echter Testanruf von
aussen), erklaert das Richtungs-Gate lueckenlos, warum look_up 0/12 (bzw. 0/19) feuerte,
waehrend der Bench (der vermutlich mit `direction: "outbound"` konstruierte Turns nutzt)
5/5 feuerte. Das ist exakt die im Befund beschriebene Bench/Live-Diskrepanz.

**Nicht belegt, weil nicht eingesehen:** ob der konkrete Owner-Testanruf tatsaechlich
inbound war. Das steht nicht im Code, sondern in den Call-Logs/Transkripten des jeweiligen
Anrufs. Ebenso nicht geprueft: ob alle 12 bzw. 19 gemessenen Live-Turns aus Inbound-Calls
stammen, oder ob darunter auch Outbound-Calls waren, bei denen look_up trotz erfuellter
Richtung nicht feuerte (das waere ein ZWEITER, verschiedener Defekt mit anderer Wurzel,
z.B. Tool-Wahlverhalten wie bei AL-D3/get_consult).

## Ergebnisruecklauf (zweite Teilfrage: "wird das Ergebnis in die Antwort zurueckgefuehrt")

`performLookupRequest` (Zeile 87-121) fuehrt bei Treffer `store.countCallLookup`,
`bookLookupSearchFee`, ruft `provider.searchFacts` auf und mergt `facts` — das tool_result
geht laut Kopfkommentar (Zeile 33-35, "Treffer landet in call.context.key_facts") in den
Kontext, den `assistantContextSection` rendert. Diesen Pfad habe ich NICHT bis ins Detail
(assistantContextSection, key_facts-Merge-Stelle) nachverfolgt — fuer B-4 nicht
entscheidend, da das Gate schon vorher (Registrierung im Werkzeugsatz) greift und der
Aufruf bei Inbound nie stattfindet. Waere fuer einen ZWEITEN Befund relevant, falls sich
"feuert bei Outbound trotzdem nicht / Ergebnis kommt nicht an" als eigenstaendiges Problem
herausstellt.

## Was das strukturell bedeutet

Kein Bug im engeren Sinn: das Gate tut exakt das, was sein Kommentar beschreibt, und ist
eine bewusste Sicherheitsentscheidung (fremde Inbound-Anrufer sollen keine Suchen
ausloesen koennen — Kosten- und Abuse-Schutz). Der Konflikt liegt auf Produktebene: Hermes
soll laut CLAUDE.md auch "persoenlicher Assistent" sein, bei dem der OWNER selbst anruft
(Personal-Assistant-Kette). Das Gate unterscheidet aber nicht zwischen "der Owner ruft
seine eigene Nummer an" und "ein Fremder ruft an" — beides ist `direction === "inbound"`.
Falls der Owner-Testanruf ein Eigenanruf war, ist look_up fuer den wichtigsten
Personal-Assistant-Use-Case (Owner fragt unterwegs etwas) durch dieses Gate strukturell
unerreichbar, unabhaengig von Prompt-Formulierung.

## Loesungsskizze (NICHT umgesetzt, nur Skizze fuer die Phase)

Falls Owner-Eigenanrufe erlaubt werden sollen: das Gate braucht einen dritten Zustand
neben outbound/inbound-fremd, naemlich "inbound, aber Anrufer ist der Owner selbst"
(vermutlich ueber Nummer-Abgleich `call.from` gegen die hinterlegte Owner-Nummer, analog zu
Mustern wie `owner-tenant-null-numbers`/`findActiveNumber`). Das ist eine
Sicherheitsentscheidung (Regel 5/Pre-Mortem: wer authentifiziert, dass der Anrufer
wirklich der Owner ist — Anrufer-ID ist faelschbar), die der Owner selbst treffen muss,
nicht implizit im Code.

## Rueckweg

Reine Lesearbeit, keine Aenderung vorgenommen.

## Risiko (Pre-Mortem)

Diese Wurzel beruehrt ein bewusst gesetztes Sicherheits-Gate ("FREMDE Inbound-Anrufer
duerfen keine Suche ausloesen"). Jede Phase, die B-4 bearbeitet, darf dieses Gate NICHT
aufweichen (keine Suche fuer echte Fremdanrufer) — sie darf hoechstens einen zusaetzlichen,
sauber begruendeten Faktor einfuehren, der Owner-Eigenanrufe von Fremdanrufen
unterscheidet, und das nur nach ausdruecklicher Owner-Entscheidung. Ein falsch gebauter
Faktor (z.B. Anrufer-ID ungeprueft als "ist der Owner" werten) waere ein Auth-/Abuse-Loch:
jeder, der die Owner-Nummer spooft, bekaeme kostenpflichtige Suchen bei einem Fremdgespraech.

## Messgroesse fuer den Pruefstand

Ob der konkrete Owner-Testanruf inbound oder outbound war, plus Anteil Inbound/Outbound
an den 12-19 gemessenen Live-Turns ohne look_up-Feuerung — aus dem Call-Log/den
Transkripten des Pruefstand-Anrufs ablesbar (`call.direction` pro Turn).
